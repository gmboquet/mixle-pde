# mixle-pde 0.7.0 release readiness checklist

Scope note (mirrors `mixle` core's `release-checklists/README.md`): `mixle-pde` ships alongside
`mixle` and its other sibling packages as part of a coordinated family release, but cross-package
coordination (lockstep versions, family co-install, publication order) is the release owner's
responsibility and is tracked outside this repo. This checklist covers `mixle-pde` on its own:
build, dependency correctness, tests, lint, hygiene, and docs, verified against the exact commit
that will sit on this branch.

Status legend: `TODO` (no evidence yet) / `PARTIAL` (evidence incomplete or not against the exact
commit) / `DONE` (verified against the exact release commit, evidence recorded inline) /
`EXCLUDED` (explicitly out of scope, reason given).

Repo: `github.com/gmboquet/mixle-pde`. Tooling actually used here (from `pyproject.toml`,
`.github/workflows/tests.yml`, `CONTRIBUTING.md`): `pytest` (+ `pytest-xdist`, `-n auto`) for tests,
`ruff==0.15.17` for lint/format, `setuptools`/`build` for packaging, Sphinx (`furo` theme) for docs.

Final commit verified end-to-end: `ba8c520e27076f07bf56b37d32e4cafc4e13e294` on `release/0.7.0`.

## 4. Dependency correctness — DONE

- **Real bug found and fixed**: `mixle_pde/ops.py`'s `make_ops()` (`_Ops.__init__`) does
  `import torch` unconditionally with no fallback backend, and 40 of `mixle_pde`'s 66 submodules
  import torch directly — it is a required runtime dependency. It was declared only under the
  `test` extra. Reproduced the failure: installing `mixle-pde` per the README's own "Install"
  section (no extras) and running the README's own "Run a forward solver directly" example raised
  `ModuleNotFoundError: No module named 'torch'`. Fixed by moving `torch>=2.0` into
  `[project].dependencies` (see gate 2) and correcting the README/CONTRIBUTING text that implied
  installing `mixle` alone brings torch (`mixle`'s own PyPI metadata shows torch/numba are
  `mixle`'s optional extras, not base dependencies).
- Reverse direction: `numpy` and `scipy` are declared and both are directly imported (60 files
  import numpy directly; `scipy.sparse` is used in `em_diffusion_3d.py`, `fem.py`,
  `field_inversion.py`, `field_priors.py`, `flow.py`, `flow3d.py`, `geophysics.py`, `latent.py`,
  `multiphysics.py`, `nonlinear.py`, `pde_solve.py`, `plate.py`, `two_phase.py`). No declared
  dependency goes unused; no import lacks a declared dependency.
- Optional dependency `xarray` (the netCDF/WOA-Argo/GEBCO loader path in `env_data.py`) is
  correctly guarded: not declared as a dependency, and `tests/env_data_test.py` skips the round
  -trip tests with a clear reason (`SKIPPED ... xarray required for the netCDF loader round-trip`)
  when it is absent, while a separate test in the same file verifies that a *missing*-dependency
  `ImportError` correctly names the missing backend module. No numba, mpi4py, or jax usage
  anywhere in `mixle_pde` (those are `mixle` core optional extras, irrelevant here).
- `mixle` itself: installs and imports correctly at the declared floor (`mixle==0.7.0` from PyPI;
  see gate 3), and the plugin's full test suite passes against it (gate 5).

## 5. Test rigor — DONE

- Full suite, editable install against the final commit `ba8c520e27076f07bf56b37d32e4cafc4e13e294`, Python 3.12.12:
  **616 passed, 2 skipped, 11 subtests passed, 0 failed** (`pytest -q`, ~156-204s wall time
  across repeated runs). Re-run identically against the non-editable, installed **wheel** (gate 3):
  same result.
- **4 real, deterministic (non-flaky, fixed-seed) failures were found and fixed** against the
  `mixle>=0.7.0` floor — none were present/possible to observe until the floor was actually pinned
  and tested, since CI previously tracked `mixle`'s `main` branch at whatever commit happened to be
  tip on a given day:
  1. `capabilities.run_required_modeling_checks()` raised `TypeError` (see gate 2/6 detail).
  2. `field_assimilation_test.py::...propagates_future_observation_backward` and the matching
     `capabilities.py` scenario asserted the wrong direction of an uncertainty comparison for an
     RTS smoother under amplifying dynamics (see gate 6 detail; verified by hand-deriving the
     Kalman-filter/RTS-smoother recursion for the exact 1-D scenario and confirming the code's
     output matches the closed-form expectation).
  3. `earth_scenarios_test.py::...returns_improved_posterior` and the matching `capabilities.py`
     scenario had a near-zero-margin, seed-dependent comparison because the synthetic gravity
     observation's declared noise covariance was never actually realized (see gate 6 detail);
     swept ~25 seeds x 7 sample sizes to confirm the fix (noise realization + a more representative
     survey precision) makes the comparison robust rather than a coin flip.
  4. `field_priors_test.py::test_temporal_precision_couples_adjacent_times` violated
     `FieldGaussianPrior`'s own "proper prior" validation (`marginal_precision > 0`), which has been
     in place since the class was introduced — this test could never have passed since it was
     added.
- Numerical-correctness coverage (not just import smoke tests) is real and exercised: spot-checked
  several solver test files for closed-form/analytic assertions, e.g.
  `tests/wave3d_test.py` (`assertLess(rel, 0.05)` against an analytical normal-mode frequency;
  `assertLess(drift, 0.01)` energy-conservation check over a run) and `tests/flow_test.py`
  (`assertLess(...)` against an analytic finite-difference gradient; a bounded-flow no-blow-up
  check). This matches `CONTRIBUTING.md`'s stated acceptance bar ("every solver ships with a test
  that checks it against an exact analytical solution... agreement with a closed-form reference is
  the acceptance bar, not just 'it runs'"), and `mixle_pde.assert_required_modeling()` /
  `readiness_report()` (the package's own runnable capability self-check, now fixed — gate 2/6)
  independently exercise manufactured-solution, synthetic-recovery, and posterior-calibration
  checks across all 8 default required capabilities: **31/31 scenarios pass.**
- Python 3.10 (the other half of CI's matrix) was not independently re-run locally in full (the
  shared scratch disk this pass ran on hit `ENOSPC` partway through a second full dependency
  install — the disk is shared across several concurrent release passes on sibling packages on
  this machine); the 3.10 leg is instead verified by the `workflow_dispatch` CI run against the
  final commit, which does run both 3.10 and 3.12 (see gate 8).
